## 二、架构评价

| 方面 | 评分 | 说明 |
|---|---|---|
| **分层** | ✅ 清晰 | `Services`（无状态 enum/actor）/ `Views`（SwiftUI）/ `Components`（可复用原子组件）/ `Theme`（设计 token）界限清晰 |
| **数据流** | ✅ 一致 | SwiftData `@Query` + `@Bindable` + `@AppStorage`，全项目统一的响应式模式 |
| **组件复用** | ✅ 优秀 | `GlassCardView` / `TicketCardView` 通用性强，6 种票据类型复用同一组件，per-type 布局在 `TicketCardView` 内条件分支 |
| **并发安全** | ⚠️ 需检查 | `SigningService` 用 actor 正确；但 `CameraService` 的 `nonisolated(unsafe)` 存在风险 |
| **扩展性** | ✅ 良好 | 新增票据类型只需 4 步：增 `TicketType` case → 增 `TicketTheme` palette → `TicketCardView` 增 info section → `TicketParser` 增 extract 方法 |

### 设计亮点

- **设计 token 系统**：`AppSpacing` / `AppAnimation` / `TicketTheme` 全项目统一使用，无离散常量散落
- **Glassmorphism 组件**：`GlassCardView` 考虑了 `rotation3DEffect` 离屏渲染导致的 Material 变灰问题，有 `useStaticBackground` 兜底
- **HIG 44pt 触控目标**：通过 `.frame(36).background(...).clipShape(Circle()).frame(44).contentShape(Circle())` 模式干净实现
- **零依赖**：不使用任何第三方库，所有功能（条码生成、OCR、地图快照、StoreKit）均通过系统框架实现

if !isPro {

### R2 — iCloud 同步开关无效

**文件**：
- `Passo/Views/Settings/SettingsView.swift`（第 120 行 — Toggle 绑定）
- `Passo/PassoApp.swift`（第 16 行 — `ModelConfiguration` 固定 `cloudKitDatabase: .none`）

**问题**：`SettingsView` 中的 iCloud 同步 Toggle 绑定 `@AppStorage("iCloudSyncEnabled")`，但 `PassoApp.swift` 的 `ModelConfiguration` 在创建容器时固定写死 `cloudKitDatabase: .none`。无论用户如何拨动此开关，SwiftData 都不会启用 CloudKit。

**风险**：用户信任问题——开关表现为可交互，但实际不生效。如果用户依赖此开关管理数据隐私，会产生数据丢失或隐私误解。

**修复方案**：方案 A（推荐）——在 `PassoApp` 启动时动态读取 `@AppStorage("iCloudSyncEnabled")` 选择 `ModelConfiguration`：

```swift
private static func makeContainer(iCloudEnabled: Bool) -> ModelContainer {
    let config = ModelConfiguration(
        groupContainer: .none,
        cloudKitDatabase: iCloudEnabled ? .privateCloudDatabase : .none
    )
    ...
}
```

方案 B（快速）——移除该开关及相应 `@AppStorage`，在 CloudKit 部署完成前不暴露此选项。

### R3 — Share Extension 硬编码 App Group ID

**文件**：
- `PassoShareExtension/ShareViewController.swift`（第 20 行）
- `Passo/Services/ShareImportService.swift`（第 12 行）

**问题**：两个文件硬编码 `group.com.passo.app`。当团队 ID 与此不匹配时（企业账号、不同开发者账号、测试环境），Share Extension 和主 App 之间的数据传递会静默失败，不产生任何错误日志。

**风险**：多开发者协作环境中 100% 失败，调试需要花费大量时间才能定位根因。

**修复方案**：

```swift
// 改为动态读取
static let appGroupID: String = {
    Bundle.main.object(forInfoDictionaryKey: "AppGroupIdentifier") as? String
        ?? "group.com.passo.app"  // 默认回退
}()
```

并在 `project.yml` 或 Xcode build setting 中统一配置。

### R4 — 免费额度检查有时序竞态

**文件**：
- `Passo/Views/Scan/RecognitionConfirmView.swift`（第 315–320 行）
- `Passo/Views/Scan/PhotoImportView.swift`（第 152–157 行）

**问题**：两处各自独立使用 `@Query private var allTickets: [Ticket]` 检查免费额度，存在时序窗口：用户在同一月内通过两个不同的入口先后导入，各通过各自的 `@Query` 检查，导致月度总导入数超过 5 张限制。

**风险**：每月最多多导入 2 张（两个入口各 1 张）。

**修复方案**：将配额检查逻辑抽取到 `StoreService`：

```swift
// StoreService 中集中管理
@MainActor
func remainingFreeImports(in context: ModelContext) -> Int {
    let startOfMonth = Calendar.current.date(
        from: Calendar.current.dateComponents([.year, .month], from: Date())
    ) ?? Date()
    let fetchDescriptor = FetchDescriptor<Ticket>(
        predicate: #Predicate { $0.importedAt >= startOfMonth }
    )
    let count = (try? context.fetchCount(fetchDescriptor)) ?? 0
    return max(0, 5 - count)
}
```

## 六、中等问题（🟡）

### M1 — `CameraService` 的 `nonisolated(unsafe)` 数据竞争风险

**文件**：`Passo/Services/CameraService.swift`（第 56 行）

```swift
nonisolated(unsafe) private var lastOCRFrameTime: CFTimeInterval = 0
```

**问题**：`captureOutput(_:didOutput:from:)` 被 `AVCaptureVideoDataOutput` 在后台线程回调。虽然方法被提交到 `ocrQueue` 串行队列执行，但 Apple 文档未保证 `AVCaptureVideoDataOutput` 的回调始终在同一个队列上——系统可以根据资源调度在不同后台线程上调用此方法。

**风险**：`lastOCRFrameTime` 没有使用同步原语保护，在高帧率场景下可能触发数据竞争。当前风险较低（写后立即读，且读写在同一个队列的方法体中），但不是安全的并发模式。

**修复方案**：

```swift
import os

let lastOCRFrameTimeLock = OSAllocatedUnfairLock()
private var _lastOCRFrameTime: CFTimeInterval = 0
private var lastOCRFrameTime: CFTimeInterval {
    get { lastOCRFrameTimeLock.lock { _lastOCRFrameTime } }
    set { lastOCRFrameTimeLock.lock { _lastOCRFrameTime = newValue } }
}
```

### M3 — `WalletPresenter` 的 `containsPass` 时序问题

**文件**：`Passo/Views/Settings/WalletPresenter.swift`（第 60–63 行）

**问题**：`addPassesViewControllerDidFinish` 回调中新建 `PKPassLibrary()` 实例并立即调用 `containsPass(pass)`。新创建的 pass 可能在短暂延迟后才出现在 library 中——如果用户快速关闭 sheet，`containsPass` 可能返回 `false`，导致 `onCancelled` 被误触发。

**修复方案**：

```swift
func addPassesViewControllerDidFinish(_ controller: PKAddPassesViewController) {
    controller.dismiss(animated: true) { [weak self] in
        // 延迟 0.5 秒检查，避免时序竞态
        DispatchQueue.main.asyncAfter(deadline: .now() + 0.5) {
            let library = PKPassLibrary()
            if library.containsPass(self?.pass ?? PKPass()) {
                self?.onSuccess?()
            } else {
                self?.onCancelled?()
            }
        }
    }
}
```

### M4 — `PassDetailView` 的 `toggleReminder` 未标注 `@MainActor`

**文件**：`Passo/Views/Detail/PassDetailView.swift`（第 345–349 行）

```swift
@MainActor
private func toggleReminder(enabled: Bool) async {
    // ...
}
```

### M6 — `PassBuilder` 中 DataMatrix 回退不准确

**文件**：`Passo/Services/PassBuilder.swift`（第 163 行附近）

**问题**：DataMatrix 格式被映射到 `PKBarcodeFormatQR`。Apple Wallet 原生支持 `PKBarcodeFormatPDF417`，它在解码能力上与 DataMatrix 更接近（均为 2D 矩阵码）。虽然 Wallet 客户端在无法渲染时会自动回退，但使用 QR 可能在 Wallet 中显示完全不同的条码样式。

**修复方案**：

```swift
case "DataMatrix":
    self = .code128  // PKBarcodeFormatCode128, 更通用的回退
```

## 八、当前 Diff 审查

### 8.1 风险点

#### D1 — AddImportSheet 转场时序

`ContentView.swift` 中：

```swift
.sheet(isPresented: $showAddSheet) {
    AddImportSheet(
        onScanTapped: {
            showAddSheet = false
            DispatchQueue.main.asyncAfter(deadline: .now() + 0.3) {
                showScanSheet = true
            }
        },
        ...
    )
}
```

**风险**：
- `0.3s` 硬编码延迟在低端设备（iPhone SE, iPhone 12 mini）上可能不够
- sheet dismiss 动画 + `fullScreenCover` 呈现之间存在可见间隙
- 没有取消处理：用户在 0.3s 间隙内快速操作可能导致状态不一致

**建议**：
1. 在 `AddImportSheet` 的 `onDisappear` 中触发延迟，保证序列化
2. 或者使用 SwiftUI 的 `dismiss` 环境值 + `.animation(.default.delay(0.3))` 替代手动 `asyncAfter`

#### D2 — WalletView 移除底部操作栏

`WalletView` 删除了 `stickyImportBar`（空状态时）和 `actionBottomBar`（非空时）。添加入口完全转移到 tab bar 的 `+` 按钮。

**风险**：用户发现性降低——"+"按钮在 tab bar 上，而 tab bar 可能在 WalletView 滚动时被 `safeAreaInset` 遮挡。用户可能找不到添加票据的入口。

**建议**：在 `WalletView` 空状态中保留至少一个显式的 CTA 按钮，或确保 tab bar 在滚动时始终可见。

#### D3 — radius token 变化

多处 `RoundedRectangle(cornerRadius: 14)` → `AppSpacing.radiusButton = 12`。圆角从 14pt 减到 12pt。

**风险**：设计师需确认此变化是否为预期。如果设计规范维持 14pt，应调整 `AppSpacing.radiusButton` 的值而非在每处用 token 替换后偷偷改值。

## 十、总结

### 核心强度

- **架构清晰**：零外部依赖、一致的 MVVM 风格、design token 全项目统一
- **组件复用度高**：6 种票据类型共享 `TicketCardView`，通过主题系统区分
- **Stubs 全部落地**：对比 `CLAUDE.md` 列出的 5 个技术 stubs，代码层已全部实现——项目已跨越"原型/概念验证"阶段
- **设计质量**：`GlassCardView` 考虑了离屏渲染 Material 变灰问题，有明确的兜底方案；HIG 44pt 触控目标通过 `contentShape(Circle())` 模式干净实现

### 最需关注的 3 个风险

1. **签名节点未部署** — 用户看到"添加到 Wallet"按钮但无法使用，是用户体验的根本阻塞点
2. **截图导入绕过免费额度** — 如果 Pro 订阅是收入模型，这是需要快速修补的计费漏洞
3. **iCloud 同步开关无效** — 产生用户信任问题，可能在 App Store 评价中招致差评
